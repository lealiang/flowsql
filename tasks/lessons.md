# 经验教训

## L1: 不要为了探测元数据而消费数据流

**来源**：DatabaseChannel Phase 7 — SqliteDriver::CreateReader bug 修复

**问题**：`CreateReader` 中为推断列的 Arrow 类型，先调用 `sqlite3_step` 读取第一行判断类型，再 `sqlite3_reset` 重置。导致两个 bug：
1. `sqlite3_reset` 后带 WHERE 的查询返回空结果集
2. `sqlite3_step` 在 SQLITE_DONE 后自动 reset 重新执行，数据被重复读取

**原则**：当需要从有状态的游标/迭代器中获取元数据（Schema、列类型等）时，使用声明式 API（如 `sqlite3_column_decltype`）而非命令式 API（如 step 一行再 reset）。后者会改变游标状态，而状态恢复在不同查询条件下行为不一致，是隐蔽 bug 的温床。

**推广**：有状态对象（游标、流、迭代器）到达终态后，不要假设"再次调用会安全返回终态"。必须在应用层显式跟踪终态（如 `done_` 标志）。

## L2: 接口设计要充分考虑职责分离

**来源**：Sprint 1 回顾 — Pipeline 和 IChannel 接口重构

**问题**：
1. Pipeline 职责过重：负责 Channel ↔ DataFrame 转换，代码复杂度高
2. IChannel 接口混杂：生命周期、元数据和数据操作混在一起，难以扩展

**原则**：
- **单一职责原则**：每个接口只负责一件事
- **接口分层**：生命周期、元数据和数据操作分离
- **职责下沉**：通用逻辑上提，特定逻辑下沉

**解决方案**：
- Sprint 2 中将 Pipeline 重构为纯连接器，数据转换职责下沉
- IChannel 基类只保留生命周期和元数据，数据读写下沉子类（IDataFrameChannel/IDatabaseChannel）

## L3: 静态库单例问题

**来源**：Sprint 2 回顾 — PluginRegistry 单例失效

**问题**：libflowsql_framework.a 静态库链接到多个 .so（主程序和 bridge.so）时，每个 .so 有独立的 PluginRegistry 单例实例，导致插件注册失效。

**原则**：
- **避免静态库单例**：静态库链接到多个 .so 时单例失效
- **优先使用共享库**：或回归纯插件架构

**解决方案**：
- Sprint 3 中删除 PluginRegistry 和 libflowsql_framework.so，回归纯 PluginLoader 架构
- Pipeline/ChannelAdapter 移入 scheduler.so，避免跨 .so 共享状态

## L9: 集成测试必须走完整生产路径，禁止绕过插件层

**来源**：Sprint 4 回顾 — 测试策略根本性错误

**问题**：`test_mysql_driver.cpp` 直接 `#include` 驱动头文件、`new MysqlDriver()` 调用底层 API，绕过了 `PluginLoader → IDatabaseFactory → IDatabaseChannel` 的完整生产路径。这类测试只验证了零件，无法发现插件加载、工厂注册、Channel 生命周期管理等集成层面的 bug。`test_plugin_e2e.cpp` 的 double-loading 堆损坏问题，正是因为测试直接链接了 `flowsql_database.so` 才暴露，而驱动层测试永远不会发现这个问题。

**原则**：集成测试必须走完整生产路径。对于插件架构，测试入口是 `PluginLoader::dlopen`，而非 `#include` 驱动头文件。

## L10: 测试数据必须覆盖所有声明支持的类型

**来源**：Sprint 4 回顾 — INT32 类型处理 bug 发现滞后

**问题**：`MysqlBatchWriter::BuildRowValues()` 对 `INT32` 没有处理分支，但测试数据只用了 `INT64`/`DOUBLE`/`STRING`，`INT32` 路径从未被覆盖，导致 bug 在 Sprint 主体开发完成后才被发现。

**原则**：写入路径的测试数据必须系统性覆盖所有声明支持的 Arrow 类型（INT32/INT64/FLOAT/DOUBLE/STRING/BOOL 等），不能只用"方便构造"的类型。类型分支覆盖是写入路径测试的最低要求。

## L11: 测试目标必须显式 -UNDEBUG，assert 是测试的最后防线

**来源**：Sprint 4 回顾 — assert 被 NDEBUG 静默禁用

**问题**：顶层 `CMakeLists.txt` 的 Release 配置传递了 `-DNDEBUG`，测试二进制中所有 `assert` 被预处理器删除，测试运行"通过"但断言从未执行。`batch` 为 null 时 `batch->num_columns()` 直接 SIGSEGV，而测试无法捕获。

**原则**：每个测试目标的 `CMakeLists.txt` 必须显式加 `target_compile_options(... PRIVATE -UNDEBUG)`。关键错误检查不依赖 assert，改用显式 `if` + `printf` + `exit(1)`，确保在任何编译配置下都能中止。

## L12: 涉及共享对象的接口必须有多线程并发测试

**来源**：Sprint 4 回顾 — 多线程并发测试完全缺失

**问题**：`DatabaseChannel::CreateReader/CreateWriter` 是多线程共享入口，整个 Sprint 4 没有一个并发读写测试。连接池并发安全有测，但上层 Channel 的并发行为无测。

**原则**：凡是可能被多线程并发调用的接口（Channel、Factory、Pool），Story 验收标准中必须包含多线程测试用例，验证：① 无 crash；② 无数据串扰；③ 资源无泄漏（in_use 归零）。

## L14: 密码/认证相关测试禁止用 SQLite 替代

**来源**：Sprint 5 TQ-B4 — 密码重启解密测试用 SQLite 代替 MySQL/ClickHouse

**问题**：TQ-B4 用 SQLite `:memory:` 测试"带密码通道重启后解密验证"。SQLite 完全忽略密码字段，`Get()` 成功只证明 SQLite 连接成功，与密码解密无关。这条测试无法验证"AES-256-GCM 解密 → 密码传给驱动 → 驱动用密码认证"的完整路径，制造虚假覆盖。

**原则**：凡是涉及密码、认证、加解密的测试，**必须使用真实校验密码的数据库**（MySQL 或 ClickHouse）。SQLite 不校验密码，用它测试认证路径等于没有测试。测试必须能在密码错误时失败，才能证明密码正确时的成功是有意义的。

**推广**：更一般地，测试所用的替代品必须与被测路径在关键行为上等价。如果替代品对被测特性无感知（如 SQLite 对密码无感知），则该替代品无效。

**问题**：Sprint 4 的测试策略存在系统性偏差——所有选择都在降低测试通过的阻力，而不是提升测试发现问题的能力：
- 用 SQLite `:memory:` 替代 MySQL：启动快、不依赖外部环境，但不是生产路径
- 直接 `new MysqlDriver()` 绕过插件层：代码简单，但集成层 bug 永远不会暴露
- `assert` 被 NDEBUG 删除：测试永远不会因断言失败而中止，制造虚假绿灯

这三个选择的共同动机是降低阻力。但**一个永远通过的测试套件，价值为零，甚至是负值**——它制造虚假安全感，让团队相信代码是正确的，而实际上什么都没有验证。

NDEBUG 问题尤其严重：它破坏的不是单个测试用例，而是整个测试体系的可信度基础。整个 Sprint 期间"测试全部通过"是一个谎言，而没有人察觉。

**原则**：
- 测试的价值在于它能在代码出错时**失败**，而不是在代码正确时通过
- 测试环境应尽量贴近生产环境，而不是选择最方便的替代品
- 任何让测试"更容易通过"的决策，都要先问：这会不会同时让测试"更难发现问题"？
- 测试基础设施（编译配置、断言机制）的可信度，优先于测试用例数量

## L15: IPlugin 生命周期必须批次调用，禁止逐个走完整生命周期

**来源**：Sprint 6 架构讨论 — RouterAgencyPlugin 方案前置条件

**问题**：`main.cpp` 的 `RunService()` 循环调用 `LoadPlugin()`，而 `LoadPlugin()` 内部是 `loader->Load()` + `loader->StartAll()` 一气呵成。导致每个插件加载后立即启动，后续插件的接口尚未注册。当 RouterAgencyPlugin 在 `Start()` 中 `Traverse(IID_ROUTER_HANDLE)` 收集路由时，排在它后面加载的业务插件还不存在。

**原则**：插件加载必须分阶段批次执行——先所有插件 Option()，再所有插件 Load()，最后所有插件 Start()。禁止逐个插件走完整个生命周期。这是 IPlugin 接口的设计本意：Load() 解决依赖绑定，Start() 启动运行，两个阶段之间所有插件的接口必须已注册完毕。

**修正**：`RunService()` 拆为两阶段——先循环加载所有插件（注册接口 + Load），再统一调用 `StartAll()`。

## L58: 阶段内模块交接优先使用结构体，不用序列化绕路

**来源**：Sprint 21 BaselineB — B1 `BootstrapSeed` 向 B2 `Online Rolling Core` 交接方式纠正

**问题**：如果 B1 先把 `BootstrapSeed` 导出成 JSON，再让 B2 重新 parse / load，等于把进程内阶段交接退化成外部持久化协议。这样会引入不必要的解析成本、格式耦合和错误面，也容易让 B2 core 误依赖 JSON schema。

**原则**：同一进程、同一任务内的阶段交接必须优先使用明确的内部 C++ 结构体。序列化只服务于持久化、审计、跨进程导入、调试和重启恢复，不作为热路径或主路径的模块边界。

**修正**：`B1 -> B2` 的主路径使用 baseline task 内部持有的 `BootstrapSeed` 结构体；该结构体不进入 `framework/interfaces` 公共 ABI。如未来需要从已保存 seed 恢复，应在 baseline plugin 内部先反序列化为结构体，再进入 rolling 初始化流程。

---

## L16: 删除旧链路时必须保留仍有迁移价值的离线产物能力

**来源**：Sprint 21 BaselineB B1 — Relation 旧在线路由删除后的能力缺口

**问题**：将旧 baseline 的在线 relation route / shadow / candidate / rebuild 链路删除时，如果连“历史 relation 数据聚合成 routed value/ratio 摘要基线”的能力也一起丢弃，就会导致 Optional Bootstrap Engine 无法为后续 Online Rolling Core 提供 relation 摘要 seed。

**原则**：清理旧在线链路时，要区分“旧热路径控制流”和“可迁移的离线产物能力”。前者应删除，后者应改造成 B1-only 离线 bootstrap 能力，并通过测试证明历史数据能产出可交给 rolling 阶段使用的 seed。

## L16: 测试数据路径属于运行时输入，禁止写入 CMake

**来源**：Baseline value replay 示例程序实现纠偏

**问题**：为了让测试程序读取指定 CSV，曾试图把数据文件路径通过 `target_compile_definitions(...)` 写进 `CMakeLists.txt`。这会把本应由调用者决定的运行时输入，错误提升为构建期配置，导致：
- 测试目标与某个固定数据文件强耦合
- 上游调用方式僵化，换一份数据必须重新配置/编译
- `CMake` 混入环境性、临时性参数，削弱构建脚本可维护性

**原则**：凡是数据文件路径、样本输入、测试数据集这类运行时可变项，默认都必须通过程序参数、配置文件或代码内明确默认值处理；禁止写入 `CMake` 作为编译期常量，除非需求本身就是生成固化产物。

**修正**：Baseline replay 示例统一改为命令行传参读取 CSV，`CMake` 只负责目标构建与依赖声明，不承载数据路径。

## L16: 高基数 key 的并发状态禁止使用 per-key mutex

**来源**：Sprint 20 BaselineA 最终复审 — 基线训练热路径锁粒度收口

**问题**：面对“少量 task、海量 key”的基线训练场景，直觉上容易把单 task 全局锁细化成“每个 key 一把 mutex”。这会把锁对象数量做成高基数常驻状态，带来明显的内存边界风险、生命周期管理复杂度和跨 key 来源读取时的多锁排序问题。

**原则**：
- 高基数 key 的运行时状态，锁粒度只能收口到**固定数量的 shard/striped lock**，不能按 key 动态分配 mutex
- 若热路径同时维护公共时序状态与算法运行时状态，优先合并到同一个 shard entry，避免一次提交连续穿过两套锁
- 涉及 configured source / cross-key fallback 的读取，必须按 shard id 有序加锁，避免死锁

**推广**：凡是“key 数量可能成千上万甚至更多”的场景，先问“锁对象数量是否有上界”。如果没有上界，就不是可接受的长期方案。

## L16: `git worktree` 必须复用主工作区第三方缓存

**来源**：Sprint 19 基线插件开发 —— `worktree` 下第三方缓存路径误落到子工作树

**问题**：在 `.worktrees/` 中配置 `CMake` 时，`THIRDPARTS_INSTALL_DIR` / `THIRDPARTS_PREFIX_DIR` 若按当前源码目录相对路径计算，会落到各自的 worktree 根目录。结果是：
- 已在主工作区编译好的第三方缓存无法复用
- 新 worktree 会重复触发 `ExternalProject` 下载 / 编译
- 一旦网络受限或缓存不完整，就会在 worktree 中报错

**原则**：
- `git worktree` 必须统一复用主工作区的 `.thirdparts_installed` 和 `.thirdparts_prefix`
- 新增第三方依赖时，先在主工作区完成一次缓存预热，再进入 `.worktrees/` 分支开发
- 头文件库也遵循同一规则，不能因为“无链接产物”就放任 worktree 首次下载，例如 `Eigen 3`

**修正**：
- `subjects.cmake` 应基于 Git 的 `common-dir` 解析第三方缓存根目录，而不是直接使用当前 worktree 路径
- 仓库规则中明确要求：新增 `thirdparts/*-config.cmake` 后，先在主工作区完成下载 / 编译 / 安装缓存，再开始 worktree 实施

## L42: 方案设计里的输入字段和术语必须直接服务算法

**来源**：Sprint 19 基线算法设计讨论

**问题**：在高吞吐基线方案设计中，容易把上游上下文字段直接塞进输入规格，例如 `sample_type` 这类只描述业务来源、却不影响建模与评分的字段；同时也容易先抛出 `phi_over`、`λ_P` 之类术语，等到后文才补解释，导致设计文档越来越大但可实施性反而下降。

**原则**：
- 输入规格中的字段，只有在它会影响训练、评分、重建或阈值语义时，才进入正式算法接口；否则留在上游语义层处理
- 术语、参数和公式第一次出现时，必须同时给出含义、作用域和默认口径，避免“先写符号、后补定义”
- 讨论和文档组织都应先给整体框架，再展开参数；不要把设计写成参数流水账

**推广**：
- 对高性能算法，优先做“算法必要性审查”，把不会改变数学行为的字段剔除在热路径之外
- 对长文档，优先做“术语闭合审查”，确保每个章节单独阅读也能理解核心语义

## L16: fnRouterHandler 精确匹配不支持路径参数，所有 IRouterHandle API 设计必须遵守此约束

**来源**：Sprint 6 Phase 3 — WebPlugin 迁移；Sprint 8 设计阶段 — CatalogPlugin API 设计

**问题**：
1. Sprint 6：`/api/operators/([^/]+)/activate` 依赖路径参数，迁移到 IRouterHandle 时被迫改为 POST + body，造成 API 破坏性变更
2. Sprint 8：新设计 `PUT /channels/dataframe/{name}/rename` 和 `DELETE /channels/dataframe/{name}` 同样使用路径参数，在设计审查阶段才发现，需要修改为 POST + body

**根因**：RouterAgencyPlugin 路由表是 `unordered_map<method:path, handler>`，`Dispatch` 用 `req.path` 做精确匹配，路径参数（`{name}`、`:id`）永远无法命中注册的路由。

**原则**：**凡是走 IRouterHandle 的 API，无论是迁移还是新设计，都不能使用路径参数**。约束范围不限于迁移场景：
1. 路径参数（`/resource/{id}`、`/resource/:id`）→ 改为 POST + body `{"name":"x"}`
2. GET + query string（`/resource?name=x`）→ 改为 POST + body（或 GET 无参数）
3. multipart 上传 → 在 WebPlugin `Init()` httplib 直接注册，不走 IRouterHandle

**检查时机**：API 设计阶段（不是实现阶段，不是迁移阶段）就必须确认所有路由模式符合约束。

## L17: 守护进程与业务逻辑必须严格分离

## L19: 前端 API 入口必须是 WebPlugin 的对外端口（8081），内部端口不对外暴露

## L20: 服务间转发地址必须有独立配置项，不能复用其他地址，不能依赖隐式环境变量

**来源**：Sprint 6 后修复 — WebPlugin db_proxy 转发到 pyworker 而非 Gateway

**问题**：`web_plugin.cpp` 把内部转发地址（`SetSchedulerAddress`）设成了 `worker_host_:worker_port_`，注释说"Gateway 模式下两者相同"，但这依赖未文档化的环境变量 `FLOWSQL_GATEWAY_ADDR`。该变量未设置时，转发打到 pyworker（18900），pyworker 不认识 `/channels/database/*`，返回 404。

**原则**：
1. 凡是"服务间转发"的地址，必须有**独立的配置项**（如 `gateway=host:port`），不能复用其他服务的地址
2. 不能依赖隐式环境变量来修正错误的默认行为；默认值本身就应该是正确的
3. 设计文档必须明确写出每个转发目标的地址来源（配置项名称、默认值）
4. 转发失败时必须打印日志（目标地址、HTTP 状态码），便于快速定位

## L23: 不要为一次 `First()` 查询引入“刷新封装”与缓存状态，直接在使用点取接口更清晰

**来源**：Sprint 8 实现修正 — SchedulerPlugin `RefreshRegistryRefs` 设计反馈

**问题**：为了处理加载顺序，新增了 `RefreshRegistryRefs()` 和成员缓存（`df_registry_` / `op_registry_`）。虽然能工作，但引入了额外状态和心智负担：调用点必须记得“先刷新再用”，代码可读性下降，且与“接口在进程内固定”这一事实不匹配。

**原则**：
1. 对于 `querier_->First(IID_XXX)` 这种轻量、稳定的接口获取，优先在使用点直接获取，避免额外封装函数
2. 除非有明确性能瓶颈或生命周期复杂性，不要缓存接口指针到成员变量
3. 设计优先级：可读性和可证明正确性 > 抽象层次感

## L24: 枚举型能力上线必须走“5层闭环”，防止后端已支持但前端入口遗漏

**来源**：Sprint 11 回顾 — Story 4.2 PostgreSQL 驱动已完成，但 Web“新增数据库通道”未暴露 PostgreSQL 类型

**问题**：后端 `DatabasePlugin` 已支持 `type=postgres`，但前端新增通道弹窗仍只包含 `sqlite/mysql/clickhouse`。结果是“能力存在但入口缺失”，用户无法通过 Web 使用新能力。

**原则**：凡是新增“枚举型能力”（数据库类型、算子类型、通道类型等），必须按以下 5 层逐项闭环，缺一不可：
1. `Contract`：统一能力清单更新（例如 `supported_types`）
2. `Backend`：工厂/驱动/核心逻辑支持
3. `Web API`：新增、查询、详情接口可透传并返回该类型
4. `Frontend`：下拉选项、表单分支、默认值、校验文案同步更新
5. `Tests`：至少一条端到端“新增并可用”用例（新增 -> 查询/浏览/执行）

**DoD（合并门槛）**：
1. PR 描述必须包含“5层闭环勾选清单”
2. Story 验收必须提供“从 Web 新增该类型并成功使用”的证据（自动化测试或可复现实测日志）
3. 未满足上述两条，不得标记 Story 完成

## L25: 实现必须服从已确认设计，禁止以“最小改动”替代架构约束

**来源**：Sprint 11 复盘 — C++ 算子插件实现偏离设计（独立插件库被实现为 Catalog 内聚能力）

**问题**：实现阶段以“最小改动、最快跑通”为优先，导致在未显式确认的情况下改变了既定架构边界；功能可用但架构产物不一致（目录/target/deploy/加载链路不匹配设计）。

**原则**：当“实现效率”与“已确认设计”冲突时，必须无条件以设计为准。任何跨模块边界、插件拆分/合并、URI 语义变化，都属于架构变更，必须先确认再编码。

**执行规则（强制）**：
1. 实现前先产出“设计条目 -> 代码落点 -> 测试点”映射清单，作为开发输入
2. 发现设计歧义或冲突时立即暂停实现，先对齐，不得自行做架构收敛决策
3. 验收顺序固定为：架构产物一致性（目录/target/deploy） -> 接口契约一致性 -> 功能行为一致性

**DoD（合并门槛）**：
1. PR 必须包含“架构一致性检查”小节，逐项勾选设计中的关键产物
2. 自动化测试除行为测试外，必须至少有一条断言覆盖关键架构产物（例如目标插件被构建并参与加载）
3. 任一关键产物与设计不一致，Story 不得标记完成

## L26: 迭代边界冻结后，不能把下迭代任务以“占位实现”形式塞入当前 Sprint

**来源**：Sprint 12 复盘修正（用户纠正）— 路径 B 接口占位范围误判

**问题**：将 `IBlockStreamChannel/IBlockStreamOperator` 空接口占位纳入 Sprint 12，虽然看起来是“小改动”，但本质上仍是路径 B 的交付内容，违反了已冻结的迭代边界，导致“计划写了但代码未落地”的进度偏差。

**原则**：
1. 迭代边界冻结后，任何属于下一迭代的事项（即使只是 header 占位）都必须显式移出当前 Sprint
2. 设计文档、计划文档、产品待办必须保持同一范围口径，禁止出现“设计在本 Sprint、代码在后续 Sprint”的错位
3. 若确需调整范围，先更新计划和 backlog，再实施代码，不允许反向补文档

## L27: 用户提问题时，必须先核查事实再改代码

**来源**：Sprint 18 过程纠偏（用户反馈）— 未完成问题核查即进入编码，导致返工与信任成本上升

**问题**：面对用户报告的现象，未先完成“是否真是问题”的证据核查，就直接改代码，容易把排查问题变成制造问题；即便最终修复，也会造成路径混乱、改动冗余和沟通成本增加。

**原则（强制）**：
1. 收到问题后，先核查事实，不得直接编码。核查至少覆盖：复现路径、相关代码路径、接口/日志/数据证据
2. 核查确认“是问题”后，先给修复方案（最小改动、影响面、风险、验证方法），经确认再改
3. 核查确认“不是问题”时，必须给出可复核证据（命令输出、代码位置、接口响应），并说明为何不改
4. 任何“先改后查”都视为流程违规，禁止再次发生

**执行清单**：
1. `Check`：复现与证据收集
2. `Conclude`：结论（是问题/不是问题）
3. `Plan`：仅在“是问题”时输出修复方案
4. `Change`：按方案实施
5. `Verify`：回归验证并给证据

## L28: 基线设计必须停留在数学异常层，不能混入业务判别层

**来源**：Sprint 19 基线设计讨论（用户纠正）— 将基线输出语义与业务判别语义混在一起

**问题**：在基线设计文档中混入了“是否值得告警”“推荐处置标签”“强 / 弱告警”等表述，导致数学异常检测层与业务判别层边界变模糊。这样会让算法规格承担不属于本层的职责，也会让后续实现和评估口径失真。

**原则（强制）**：
1. 基线层只输出数学异常结果：分数、方向、模式标签、置信度、持续性和解释证据
2. 业务异常判定、告警路由、优先级、处置建议明确属于上层系统，不在基线算法规格内展开
3. 文档措辞优先使用“数学异常结果”“风险输出”“模式标签”“强度等级”，避免直接使用“告警”“推荐处置”等业务化表达
4. 如果必须提及业务层，只能在范围 / 约束章节说明“明确不在本设计范围内”，不能继续展开其具体机制

## L29: 高基数基线设计必须采用上游聚合 + 稀疏事件驱动，不能让 `T1` 基线层内部逐窗口展开

**来源**：Sprint 19 基线设计讨论（用户纠正）— 将 `T1b` 输入表述成“基线内部按时间窗口处理原始样本”，并进一步指出 `T1a` 也必须遵守同一输入边界

**问题**：如果让基线层自己对原始指标按 `1 min` 做窗口聚合，或对所有潜在序列逐分钟展开空窗口，在“每分钟数百万指标”的规模下，吞吐和状态成本都会失控。这个问题对 `T1a` 和 `T1b` 都成立。问题不在时间窗口这一统计语义本身，而在职责边界放错了层级。

**原则（强制）**：
1. 时间窗口是上游特征聚合层的统计粒度，不是基线层内部重新做一遍的聚合流程
2. 基线层只消费上游产出的稀疏统计记录，如 `(key, feature, bucket_id, value, summary_meta)`
3. 基线层不得为所有潜在序列逐分钟补空桶；缺失应通过 `bucket_id` 跳变和 gap 规则惰性处理
4. 原始样本集合不得进入基线算法输入；若某统计量需要 `sample_count`、分位点口径等，只能以上游聚合后的摘要元数据形式携带

## L30: 通用基线算法不应硬编码物理单位，单位与数值尺度由上游特征规范统一

**来源**：Sprint 19 基线设计讨论（用户纠正）— 不应把时延类特征统一强制为 `ms`

**问题**：将时延类特征在算法层统一强制成 `ms`，会把领域相关的数值尺度假设硬编码进通用基线算法。不同业务领域对时间精度的要求差异很大，强行统一单位既不通用，也会增加无意义的转换和约束。

**原则（强制）**：
1. 基线算法层不强制规定物理单位，也不在热路径上处理单位换算
2. 单位、精度和规范数值表示由上游特征定义 / 聚合层统一保证，而不是由基线层决定
3. 基线层只要求同一 `feature` 在其生命周期内保持一致的数值表示；若表示方式变化，应视为特征口径变更并触发新特征或模型重建
4. 对通用基线而言，比“单位是什么”更重要的是“同一特征的值是否可比较、是否长期一致”

## L31: 设计基线算法规格时，不能引入不参与算法的业务语义字段

**来源**：Sprint 19 基线设计讨论（用户纠正）— `sample_type` 设计过于侵入业务，除非它实际影响基线算法

**问题**：把 `request/transaction/flow` 这类业务语义额外设计成独立字段，如果它既不影响训练目标、在线评分、阈值语义，也不影响状态更新，那它只是重复表达已包含在 `feature` 定义里的信息，会增加输入复杂度并侵入业务建模。

**原则（强制）**：
1. 只有当某个字段会实际影响基线算法的行为时，才允许进入算法规格
2. 若某语义仅用于区分特征口径，但不参与算法分支，应直接编码进 `feature` 身份或上游特征注册，而不是新增算法字段
3. 通用基线层优先依赖最小必要字段集，避免把业务分类体系下沉到算法输入
4. 任何新增字段，都必须先回答一句话：它具体影响哪条公式、哪条阈值或哪段状态机；答不上来就不要加

## L32: 上游已定义为独立 feature 的语义，不应在基线层再用字段重复表达；差异优先落到参数配置而非算法分支

**来源**：Sprint 19 基线设计讨论（用户纠正）— 既然 `avg_rtt`、`p95_rtt` 已由上游指定为独立特征，基线层就不应再按同一语义额外拆字段并做单独处理

**问题**：如果上游已经把 `avg_rtt`、`p95_rtt`、`transaction_avg_latency` 等定义成不同 `feature`，基线层再引入 `stat_type/sample_type/quantile_q` 等等价语义字段，并据此分支，就会造成语义重复、接口膨胀和实现复杂化。真正需要区分的，往往只是参数，而不是算法主干。

**原则（强制）**：
1. 已编码进 `feature` 身份的语义，不在基线层重复建字段，除非该字段会直接改变算法公式或状态转移
2. 若不同 feature 仅需要不同阈值、最小样本门槛、变换方式等，应通过每个 feature 的参数配置 / profile 表达，而不是额外引入运行时语义字段
3. 先区分“不同算法”与“同一算法不同参数”这两类问题；能用参数解决的，不上升为算法分支
4. 基线核心层优先保持统一主干，feature 之间的差异默认通过注册配置注入

---

## L33: 不可用 bucket 应在上游直接过滤为 gap，基线层不保留独立质量字段

**来源**：Sprint 19 基线设计讨论（用户纠正）— 若 `quality` 差，直接不上报给基线即可，无需新增 `quality` 字段

**问题**：在基线输入里保留 `quality` 字段，会让“不可用记录”和“有效记录”共存于同一输入协议中，迫使基线层承担数据清洗职责，增加 gate 逻辑和状态机复杂度。若不可用 bucket 的处理结论本来就是“不训练、不评分、不更新，等价于 gap”，那么保留该字段没有必要。

**原则（强制）**：
1. 不完整、可疑、不可判定的 bucket 应由上游直接过滤，不进入基线输入
2. 基线层只接收可用记录；不可用 bucket 在算法语义上统一表现为 gap
3. 若某字段只用于告诉基线“这条记录其实不要用”，优先删除该字段，并把过滤职责上移
4. 只有当质量状态会导致不同的算法行为且无法在上游消解时，才允许保留独立质量字段

## L34: 设计讨论时，术语和参数必须在首次出现处给出一句解释，不能只抛名称

**来源**：Sprint 19 基线设计讨论（用户纠正）— 类似 `phi_over` 这类术语必须带上解释

**问题**：在算法设计讨论中直接引入 `phi_over`、`m0`、`s_prior` 等术语或参数名，而不在首次出现时解释其职责，会迫使读者在多个回合间来回追溯上下文，降低设计可读性，也容易让用户误判当前讨论是在定义框架还是在做局部调参。

**原则（强制）**：
1. 任何新术语、参数或符号，在首次出现时都必须附带一句职责解释，至少回答“它是什么、解决什么问题”
2. 后续再次使用时可以只写名称，但若语义易混淆，仍应补一句简短说明
3. 文档中参数表的“含义”列必须和正文首次解释保持一致，避免前后口径漂移
4. 若某术语在当前阶段仍未收敛定义，不应直接丢出参数名，而应先说明它是“待定占位”还是“已确定概念”

---

## L35: 讨论设计时应先给整体框架，再逐块填空，避免陷入逐参数推进

**来源**：Sprint 19 基线设计讨论（用户纠正）— 需要先看到 `T2` 的整体设计框架，再逐项细化

**问题**：如果按参数一个接一个推进，用户很难判断当前讨论处于整体设计的哪个层次，也不知道哪些内容已经定稿、哪些只是局部占位。这样会让设计评审失去边界感，变成无终点的参数堆叠。

**原则（强制）**：
1. 新分型或新模块的讨论，必须先给出整体设计框架，明确各层职责和待填空项
2. 只有在用户认可整体框架后，才进入具体参数、公式或默认值的细化
3. 后续每次讨论局部参数时，都要显式指出它位于整体框架的哪一层
4. 若用户要求“继续设计”，默认优先推进框架中尚未收敛的空白块，而不是随机挑一个参数继续深入

## L36: 引入父级回退或层级基线时，必须先定义层级关系的来源，不能默认存在“父子关系”

**来源**：Sprint 19 基线设计讨论（用户纠正）— 在提出 `child model / parent model` 之前，没有先说明父子关系如何确定

**问题**：如果只说“冷启动时借用其他基线来源”，却不定义来源是谁、这层关系由谁提供、是否稳定、是否属于算法输入，就会把一个关键前提留空。这样后续实现会在“算法自动推断来源关系”与“上游显式提供来源配置”之间摇摆，造成职责边界混乱。

**原则（强制）**：
1. 任何涉及父级 / 群组 / 基线来源的设计，必须先回答来源关系由谁定义
2. 若层级关系依赖业务实体组织或路由拓扑，应优先由上游配置 / 注册层显式提供，而不是由基线算法层自行猜测
3. 只有在层级规则是稳定、通用、不会侵入业务语义时，才允许在算法规格中固化
4. 在层级来源未定义前，不应继续展开子级 / 父级切换状态机

## L37: 涉及来源借用时，统一正名为“基线来源”，并明确它是上游显式配置的可选静态元数据

**来源**：Sprint 19 基线设计讨论（用户纠正）— “父子关系如何确定”这一前提未定义，且用户进一步明确“不要叫回退基线了，正名为基线来源，并且所有特征都可用，要由上游显式配置指定”

**问题**：`child model / parent model`、`回退基线`、`基线来源链` 这类表述都容易把重点放在层级或回退动作上，误导实现把这件事做成算法内推断。实际需要的是一个更中性的统一概念：`基线来源`。它表示某个 `(key, feature)` 在冷启动或本级暂不可用时，可借用哪些已配置来源的基线输出；该能力适用于所有特征类型，并由上游在配置 / 注册层显式给出。

**原则（强制）**：
1. 在规格文档中，统一使用“基线来源”这一术语，不再使用“回退基线”“基线来源链”“父子模型”等表述
2. 基线来源适用于所有特征类型，不限于某一类检测器
3. 基线来源应定义为上游显式配置的可选静态元数据，不作为每条运行时观测的必带字段
4. 算法层只负责消费和选择可用来源，不负责推断来源关系
5. 若上游未提供基线来源配置，则算法必须能够独立运行，只是禁用该可选能力

---

## L38: 基线层不能因为正式重建而承担历史数据存储职责；历史观测应由独立历史源提供

**来源**：Sprint 19 基线设计讨论（用户纠正）— 若全量正式重建要求基线层自己保存 post-shift 历史数据，会导致基线与上游数据生产链路强耦合

**问题**：如果基线模块为了“全量正式重建”而自行持久化 bucket 级历史观测，它就会从检测器膨胀成带存储职责的数据子系统。一旦历史保存格式、保留周期、补数语义、回放接口都落在基线层，算法边界就会与上游特征聚合 / 历史查询能力纠缠在一起，增加实现复杂度和系统耦合。

**原则（强制）**：
1. 基线层默认只保存模型状态、轻量在线状态和必要元数据，不保存可重放的历史观测明细
2. 若全量正式重建需要历史数据，应由独立的历史观测源提供，如上游特征存储、统一特征仓或专门的历史查询接口
3. 算法规格应区分“在线临时基线”和“正式重建数据来源”，不能默认二者都由基线层内部承担
4. 若系统当前不存在可供正式重建的历史观测源，则 `v1` 不应强行引入基线内置存储；应降级为影子基线临时托底 + 依赖上游后续正式重建或定时重建

---

## L39: 若基线需要历史数据做正式重建，应在任务下发时注入历史数据获取回调，而不是让基线层直接依赖上游存储实现

**来源**：Sprint 19 基线设计讨论（用户纠正）— 采用方案 B，在下发基线任务时提供历史数据获取回调接口，基线正式重建按需调用该接口获取所需数据

**问题**：如果只说“正式重建时从外部历史源取数据”，但不把它收敛成明确的接口注入方式，后续实现很容易退化成基线模块直接耦合某个具体存储、SDK 或上游服务。这样会让算法层和工程接入层缠绕，既不利于复用，也不利于测试。

**原则（强制）**：
1. 历史数据能力应以回调接口或等价抽象的方式，在基线任务注册 / 下发时注入给基线层
2. 基线层只依赖“按 `(key, feature, bucket_range)` 获取历史观测”的抽象契约，不依赖具体存储类型和上游实现细节
3. 正式重建是否可执行，取决于该回调接口是否已提供且返回足够数据；不能默认基线层自己补齐历史
4. 在线评分与轻量状态更新不应依赖该回调接口，历史拉取只用于异步正式重建、回放验证等离线 / 慢路径能力

---

## L40: 基线系统的“训练”必须拆分为在线更新、增量适配和正式重建 3 层，避免把基线误解成“建好后冻结”

**来源**：Sprint 19 基线设计讨论（用户纠正）— “重训”这个词容易让人误解为基线一旦建立就停止更新，只有出问题才再次训练

**问题**：如果不区分在线轻量状态更新、影子基线之类的连续适配，以及依赖历史窗口的正式模型刷新，文档会把所有更新行为都混叫成“训练 / 重训”。这样既不利于架构分层，也会让实现者误以为“模型只有两种状态：未训练和重训”。

**原则（强制）**：
1. 基线建立后不会停止学习；每个有效 bucket 都应发生在线更新
2. 轻量、`O(1)` 的连续修正应定义为“增量适配”，如影子基线偏移、漂移证据、残差尺度等
3. 依赖历史窗口、异步执行、会重建正式模型结构参数的慢路径，统一称为“正式重建”
4. 文档中出现 `train / gate_train / training objective` 时，若无特殊说明，默认指正式模型训练样本准入与正式重建目标，而不是在线热路径逐点训练

---

## L41: 特征类型必须按数学形态分型，不能按来源分型

**来源**：Sprint 19 基线设计讨论（用户纠正）— 将 `T4` 定义为“关系模式 / 专家评分类”会把“特征的来源”误当成“特征的类型”

**问题**：`T1 / T2 / T3` 的分型依据是数学对象本身：单值时序、比例 / 率、分布差异；而“专家分数”“规则输出”“图算法分数”描述的是来源，不是数学形态。如果把来源单独定义成 `T4`，就会出现分型口径不一致：同样是单值标量，只因为来自专家模块就被分到不同类型，导致后续算法边界和示例体系持续混乱。

**原则（强制）**：
1. 特征类型必须按数学形态分，而不是按来源分
2. 外部规则、图算法、专家模型输出若进入基线，必须先判断它在数学上属于单值时序、比例 / 率，还是分布差异，再分别归入 `T1 / T2 / T3`
3. 若外部证据不需要时间基线，只作为硬规则或强证据使用，则不应新建特征类型，而应直接进入融合层
4. 在文档中，来源最多作为示例或补充说明，不得与 `Feature Type` 并列成类

## L42: Basis 相关摘要特征必须绑定明确、冻结、可比较的基准，不能混用“当前排序槽位”和“固定身份对象”

**来源**：Sprint 19 基线设计讨论（用户纠正）— `top1_share / headK_share` 这类按当前排序定义的特征，和 `stable_g[i]_share` 这类固定身份特征，如果不先明确各自依赖的 basis，就会在“是否可比较、比较的意义是什么”上持续混乱。

**问题**：当摘要特征的定义同时依赖“当前排序结果”“历史支持集”“固定头部集合”时，如果文档没有先把这些基准对象写清楚，后续很容易把不同语义的量混在一起比较。例如把“当前第一名份额”误当成“历史固定第一头部份额”，或者在 `candidate vs incumbent` 验证时直接比较来自不同 support / stable head 的摘要特征损失。

**原则（强制）**：
1. 所有 basis-dependent 摘要特征都必须先声明其依赖的冻结基准，如 `SupportExplicit`、`StableHeadSet`、`head_proto_q`
2. “当前排序槽位”特征只能表达分布形状，不能承担固定对象身份语义
3. “固定身份对象”特征必须来自冻结的历史对象集合，且该集合在模型版本内保持不变
4. 任何 `candidate vs incumbent` 的验证比较，都必须先投影到共同 `EvalBasis` 上；不能直接比较来自不同 basis 的摘要特征损失

---

## L43: 有价值但非主闭环必需的增强特征，不应升级为标准输入要求

**来源**：Sprint 19 基线设计讨论（用户纠正）— `distinct_group_count` 对 `T3` 有建模价值，但并非所有上游都能稳定定义和低成本提供 `active_count[m]`，因此应保留为可选增强，而不是标准必带字段

**问题**：在长规格讨论中，容易把“确实有检测收益”的增强特征一路抬升成“正式接入必须提供”的标准输入。这样会把主闭环与增强能力绑死，让本来可选的上游计数、元数据或辅助统计变成硬依赖，增加接入成本，也削弱方案的通用性。

**原则（强制）**：
1. 先判断某个特征是否是主算法闭环成立的必要前提，再决定它是必选输入还是可选增强
2. 只要主闭环在缺失该特征时仍可完整运行，就不应把对应上游字段写成标准必带输入
3. 对可选增强特征，文档必须同时写清楚：启用条件、缺失时的能力退化、以及为何它仍值得保留
4. 只有当上游能够稳定定义、低成本提供且广泛适用时，增强输入才应升级为标准字段

---

## L44: 领域中的常见特例不能被写成通用算法前提

**来源**：Sprint 19 基线设计讨论（用户纠正）— 对网络流量而言，`active_count[*]` 往往可以取相同值；但对更通用的业务数据，不同 `metric` 上的活跃定义未必一致

**问题**：在用网络流量场景推导通用算法时，容易把领域内常见的经验关系直接写成通用约束。例如把 `conn_count / bps / pps` 下 `active_count[m]` 常常相同这一事实，误写成“多指标共享同一个 active_count”。这样会让通用方案被具体领域绑架，后续接入其他业务数据时出现语义错位。

**原则（强制）**：
1. 通用算法中的输入语义必须按数学定义写清楚，不能依赖某个领域的常见巧合
2. 若某个关系只是在特定场景下经常成立，应在文档中明确标注为“场景特例”或“常见但非必然”
3. 对多指标输入，默认每个 `metric` 都有自己的定义、状态和统计量；只有在上游显式保证等价时，才能共享
4. 举网络流量例子时，可以说明 `active_count[conn_count]`、`active_count[bps]`、`active_count[pps]` 常常相同，但不得把这种直觉提升为通用接口假设

---

## L45: Story 开工前必须做“依赖闭合审查”，不能只看名义依赖

**来源**：Sprint 19 `Story 18.10` 实施前复盘（用户要求反思）— `planning.md` 把 `Baseline Source` 标为依赖 `18.9`，但真正的验收语义又引用了“已 ready 的正式模型”，而正式切换实际上在 `18.12` 才落地，导致编码前才暴露出依赖失效

**问题**：如果只看“Story A 依赖 Story B”这种名义依赖，而不继续核查“当前 Story 要消费的状态是谁生产的、何时生产、如何验证”，计划表面上是通的，真正到编码阶段才会发现依赖未闭合。再叠加 `design.md` 和 `plugin-design.md` 的术语口径漂移，问题会在实现前才集中爆发。

**原则（强制）**：
1. 每个 Story 开工前，必须把验收标准逐条映射到 4 个闭环：输入契约、状态生产者、选择 / 决策语义、测试验证钩子
2. 任何 Story 若要消费某个运行时状态，必须能明确指出“这个状态由哪个已完成 Story 产生”；若指出的是未来 Story，则当前 Story 不能直接开工
3. `design.md`、`plugin-design.md`、`planning.md` 对同一个术语的语义必须在开工前对齐；只要存在口径漂移，先改文档，再写代码
4. 若发现当前 Story 的语义依赖未来能力，必须在编码前二选一：要么前移最小使能能力，要么把当前 Story 的契约收口到“当前可验证、可服务”的版本，并明确后续 Story 的收紧点
5. 未完成依赖闭合审查的 Story，不得进入编码阶段

---

## L46: 代码命名必须体现工程语义，不能偷懒复用算法分类标签

**来源**：Sprint 19 关系分布实现讨论（用户纠正）— 算法文档中的 `T3` 只是分类术语，不应直接变成代码目录、文件名和结构体名

**问题**：在设计转代码时，容易图省事直接把算法分类名拿来当代码命名，例如 `t3/`、`T3TaskSpec`。这种命名对写文档时看起来省力，但对实现、维护和新成员理解都很差：它没有表达对象的工程职责，只表达“这是第三类算法”，一旦脱离上下文就几乎没有自解释能力。

**原则（强制）**：
1. 算法分类术语和代码命名必须分层处理：分类术语用于设计文档，代码命名用于表达工程职责
2. 代码中的目录、文件、类名、结构体名必须优先体现数据对象或职责语义，例如 `relation_task`、`RelationTaskSpec`、`relation_basis`，而不是 `t3`
3. 若某个概念既需要保留算法分类，又需要落到代码对象，文档中必须明确写成“算法类型 `T3`，代码命名 `relation`”这类边界说明
4. 任何新增代码设计若出现 `T1/T2/T3` 直接作为目录名、文件名前缀或核心对象名，必须在实施前重新审视并改名

---

## L47: 代码设计文档必须闭合到方法级契约与身份语义，不能停留在模块 owner 层

**来源**：Sprint 20 BaselineA 代码设计审查

**问题**：上一版 `code-design.md` 虽然已经把大部分算法能力映射到了模块，但仍存在几类“看起来有设计、实际上仍无法直接编码”的缺口：
- 只写了 `event_calendar_matcher.*`、`readiness_helper.*` 这类模块 owner，没有把 compile / match / readiness 更新的最小方法级契约写清楚
- `KeyRiskFusion` 只写了 `source_id` 概念，没有定义唯一来源身份，导致 direct task、relation routed feature、pattern fusion 在同一 `task_id` 下可能发生覆盖或混淆
- 部分边界存在自相矛盾，例如时间相位 helper 与事件命中 matcher 的职责分界没有完全收口

**原则**：
- 代码设计文档若要指导编码，必须把“谁负责什么”继续收口到“提供哪些方法、消费哪些状态、输出哪些身份”
- 任何带融合、注册表、缓存窗口的设计，都必须显式定义唯一 identity 和清理责任，不能只靠自然语言的“来源”概念
- helper 的职责边界必须单点收口；同一语义只能有一个 owner，避免实现时各模块重复解释
- 目录结构、模块清单、状态机、测试矩阵必须互相对齐；缺一项都会在编码阶段演化为临时补丁

**推广**：
- 审查代码设计时，除了看“有没有模块”，还要逐项检查：
  1. 有没有方法级契约
  2. 有没有唯一 identity
  3. 有没有生命周期清理责任
  4. 有没有测试覆盖这些边界条件

---

## L48: 设计文档中的 `?` 只能表示显式可选字段，不能混入“待定语义”

**来源**：Sprint 20 BaselineA 代码设计讨论（用户纠正）— `baseline_source_config?`、`event_calendar_spec?` 等写法容易被误解为“当前先留口子，后续再决定”

**问题**：在代码设计文档中直接写 `field?`，如果没有同步定义 absent 语义，读者很容易把它理解为“实现时再决定”。这会让设计看似完整，实际在编码阶段才暴露出语义分歧，尤其容易出现在配置字段、事件层、来源借用、诊断元数据这些地方。

**原则**：
- 文档中的 `?` 只表示“显式可选字段”，绝不能表示“待定”
- 每个 `field?` 第一次出现时，必须同时写清楚：
  1. present 时承载什么语义
  2. absent 时系统如何运行
  3. 谁负责填充或裁剪它
- 如果某字段在正式设计里其实必须存在，就不要写成 `?`
- 任何“若后续决定启用”“暂时先 absent”这类表述，若没有设计文档依据，都应立即收口为正式定义

## L49: 共享 task 的配置必须显式写出生效粒度，不能默认扩散到所有运行时 key

**来源**：Sprint 20 BaselineA `BaselineSourceConfig` 语义纠正 — 用户明确要求“按 `(key, feature)` 配置和选择来源”，而不是 task 级全局来源配置。

## L50: 系统时区与业务建模时区必须解耦，禁止把 task `tz` 直接实现成进程环境 `TZ`

**来源**：Sprint 20 BaselineA 时区收口讨论（用户纠正）— “进程所在系统的时区”和“需要建模的数据时区”是两个概念；`tz` 应作为创建 baseline 时的业务参数指定，未指定时默认中国北京时间。

**问题**：我把 task `tz` 错误地等同为进程运行环境的 `TZ`，进而提出“单时区注册 + 设置进程 TZ + 去掉热路径锁”的方案。这个思路混淆了操作系统环境语义与业务建模语义，会把 baseline task 的时间解释错误地下沉为全进程副作用，并把默认值、生命周期和多 task 并存策略都带偏。

**原则（强制）**：
1. `BaselineTaskSpec.tz` / `RelationTaskClockSpec.tz` 表示**业务数据的时间语义时区**，不是宿主进程或部署机器的系统时区。
2. 业务时区必须作为 task 创建参数显式建模；若外部配置未提供，parser 层要补默认值 `Asia/Shanghai`，不能依赖机器环境“碰巧是东八区”。
3. 任何时间 helper 若消费的是业务 `tz`，实现上必须是“显式按参数解释时间”，禁止通过修改进程级 `TZ` 环境变量来偷渡语义。
4. 设计和实现都要分别说明：
   - 进程所在系统时区：宿主环境属性
   - baseline task `tz`：建模语义属性
   两者不得混用、不得共享生命周期假设。
5. 讨论去锁、性能优化或一致性约束前，先确认锁保护的是哪一层语义；如果锁来自“进程级 TZ 切换”，正确方向应优先是消除该全局副作用，而不是把业务 `tz` 收缩成进程级单例。

## L51: 高基数运行时状态的边界控制要先做“有界清理 + 可观测性”，不要直接上复杂淘汰器

**来源**：Sprint 20 BaselineA 最终收口 — `Value/RatioDetectorCore`、`RelationTask::runtime_by_key_`、`KeyRiskFusion` 的高基数状态边界修复

**问题**：当少量 task 承载海量 key 时，运行时状态很容易长期常驻在 `unordered_map` 中。若没有边界控制，内存会随着历史 key 数单调增长；但如果一上来就引入复杂 LRU / 全量扫描，又会把热路径变成新的性能问题。

**原则**：
1. 高基数状态收口的第一步，应优先采用“固定阈值 + 有界 opportunistic prune + 明确可观测计数”的轻量方案。
2. 清理动作必须有固定上界，例如固定 `scan_limit`，禁止在热路径做全表扫描。
3. 清理触发应与单调推进的时序量绑定（如 `bucket_id`），避免同一 bucket 重复做无意义清理。
4. snapshot / service stats 必须同步暴露当前 key 数量、清理阈值和累计清理量，否则边界控制不可验证。

## L57: Bootstrap 成熟度只能基于实际训练支撑，不能基于原始输入数量

## L63: 新增运行时配置不能只写在 C++ 默认值里

**来源**：Sprint 21 BaselineB B2 实现纠偏 — 用户指出 `BaselineRolling` 相关配置不能只硬编码在头文件中，也必须记录到 `config/baseline-config-template.yaml`。

**问题**：如果新增配置只存在于 C++ 默认值，使用者无法从模板了解可调参数，strict YAML schema 也无法覆盖这些字段。后续调整默认值时，代码、模板和测试容易漂移，最终导致线上配置不可见或不可验证。

**原则（强制）**：
1. 新增运行时配置结构时，必须同步更新默认值、YAML 解析、strict schema、配置模板和最小测试。
2. 配置模板必须列出可运维调节的关键参数，不能只依赖头文件作为事实来源。
3. 如果某个参数同时被多个阶段使用，必须在阶段文档中写清最终归属，避免从旧配置结构隐式覆盖新配置结构。

## L64: 阶段设计必须对齐当前代码的实际计算边界

**来源**：Sprint 21 BaselineB B3 设计纠偏 — 用户指出检测可信度、band 校准和 monthpos 设计必须精确贴合 B2 rolling 热路径。

**问题**：如果阶段设计只写算法意图，不钉死当前代码的实际证据来源，后续实现会出现重复计入方差、用 post-update estimator 填 public result、把未成熟 daily/weekly 当成 ready component，或把 centered monthpos coeff 误当直接 offset 等偏差。这类问题不会表现为编译错误，但会让检测 band、`Z-score` 和 `can_alert` 语义失真。

**原则（强制）**：
1. 设计文档引用现有实现时，必须写清 pre-update / post-update、public result、update gate、drift evidence 各自使用哪份 evidence。
2. 基于现有方差公式扩展 detection band 时，必须拆清基础 `sigma^2`、额外观测噪声和 `sigma_floor^2`，禁止直接复用聚合后的 `obs_var - pred_var`。
3. 组件成熟度与中心线贡献必须分开描述：未 ready 组件若作为 provisional center hint 使用，必须在 evidence 中说明，并用组件缺失不确定性保守扩宽 band。
4. 从旧 bootstrap / formal model 继承的 monthpos 结构必须保留 centered basis 语义，不能把 coeff 简化为直接 offset。
