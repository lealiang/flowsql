# Sprint 19：统一基线方案与 Facebook Prophet 对比评估

## 1. 背景

本文对比的对象有两个：

- `Facebook Prophet`（下文简称 `Prophet`）：成熟的可解释时序预测 / 基线建模开源方案。
- 本 Sprint 设计中的统一基线方案：覆盖 `T1`（数值时序）、`T2`（比例 / 率）、`T3`（分布漂移）的在线异常检测框架，主文档见 `design.md`。

需要先明确一点：两者不是完全同层级的对象。

- `Prophet` 更接近“单序列预测模型 / 可解释基线模型”。
- 本方案更接近“面向异常检测的统一基线系统设计”，其中 `T1` 主干才与 `Prophet` 存在较强可比性。

因此，本文的对比不是为了回答“谁绝对更先进”，而是回答以下几个更有意义的问题：

1. `Prophet` 在哪些方面明显强于当前方案。
2. 当前方案在哪些方面不是 `Prophet` 可以直接替代的。
3. 在网络流量分析场景下，哪些思想可以借鉴 `Prophet`，哪些地方不应借。

## 2. 核心结论

结论先行：

1. 若目标是少量单值时间序列的可解释预测 / 基线，`Prophet` 的成熟度明显高于当前方案。
2. 若目标是分钟级、高基数、持续在线的异常检测系统，尤其是要统一覆盖 `T1 / T2 / T3`，当前方案的方向明显比 `Prophet` 更贴合场景。
3. 当前方案在 `T1` 的主干结构上，确实部分借鉴了 `Prophet` 一类加性分解模型的思想；但它不是 `Prophet` 的复刻版，也不是以 `Prophet` 为实现基础。
4. `Prophet` 最多只能作为 `T1` 某些场景下的可选参考，不足以覆盖 `T2` 和 `T3`，也不能直接承担本方案要求的在线漂移处理、影子基线桥接和高基数热路径。

## 3. 总体对比

| 维度 | Prophet | 当前统一基线方案 | 判断 |
|---|---|---|---|
| 核心定位 | 单序列可解释预测 / 基线 | 在线异常检测统一框架 | 不同层级 |
| 技术成熟度 | 很高，已有论文、官方文档、稳定开源实现 | 当前仍以设计为主，未完成实现验证 | `Prophet` 明显更成熟 |
| 可解释性 | 强，强调 trend / seasonality / holidays | 强，强调 `Core / monthpos / event / drift / T3` 模式 | 两者都强 |
| 适用对象 | 主要是单标量时序 | `T1` 单值、`T2` 比例 / 率、`T3` 分布漂移 | 当前方案覆盖面更广 |
| 在线能力 | 以批量拟合为主，不是在线检测框架 | 明确设计在线评分、慢路径正式重建 | 当前方案更适合在线检测 |
| 漂移处理 | 主要依赖模型重拟合与 changepoint 结构 | 漂移证据累积器 + `shadow baseline` + 正式重建 | 当前方案更贴近流量场景 |
| 高基数扩展 | 可做多序列，但海量序列成本会线性放大 | 从一开始就按高基数热路径设计 | 当前方案更适合分钟级大规模 |
| 关系分布建模 | 不擅长 | `T3` 专门覆盖 | 当前方案明显更强 |
| 工程现成度 | 高 | 低 | `Prophet` 更强 |

## 4. 算法技术对比

### 4.1 `Prophet` 的主干技术特征

`Prophet` 的经典建模形式可以概括为：

```text
y(t) = g(t) + s(t) + h(t) + e(t)
```

其中：

- `g(t)`：趋势项，支持分段线性或逻辑增长，并通过 changepoint 处理趋势变化。
- `s(t)`：周期项，通常通过 Fourier 展开表达日 / 周 / 年周期。
- `h(t)`：节假日 / 事件回归项。
- `e(t)`：剩余噪声。

`Prophet` 的优势在于：

- 模型结构非常清晰，可解释性强。
- 对业务分析人员友好，建模接口成熟。
- 针对日 / 周 / 年等常见周期的经验非常丰富。

`Prophet` 的典型短板也很明确：

- 它主要面向单序列预测，而不是在线异常检测系统。
- 它默认的更新方式仍然是重新拟合或近似 warm start，不是热路径增量评分。
- 它不处理比例分母支撑度、分布支持空间、关系结构模式这类问题。

### 4.2 当前方案在 `T1` 上与 `Prophet` 的关系

当前方案在 `T1a` 上的正式模型主干为：

```text
μ_t = μ_core(t) + h_monthpos(t) + h_event(t)

μ_core(t)
= β0
 + k * t
 + s_day(t)
 + s_week(t)
```

从技术思想上看，这一结构与 `Prophet` 存在明确相似性：

- 都采用加性分解。
- 都把趋势、周期、事件作为独立组件建模。
- 都使用 Fourier 形式表达周期。

但当前方案与 `Prophet` 有 4 个关键差异：

1. **显式去掉了活动模型中的 changepoint**

当前方案明确规定：

- `v1` 的正式模型不内建 `changepoint`
- 结构变化优先通过“漂移确认 -> 估计 `τ_hat` -> 裁剪历史重建”处理

这意味着当前方案把“结构变化”更多下沉到正式重建慢路径，而不是放进主模型结构。

2. **增加了 `monthpos` 层**

当前方案在 `Core` 之上增加了专门的月位置层：

- `day_of_month`
- `days_to_month_end`
- `last_weekday_of_month`

这不是 `Prophet` 的标准主干能力，而是针对“每月几号 / 月末 / 最后一个工作日类规律”专门设计的扩展。

3. **训练方式不同**

当前方案不是整体一次性联训，而是采用：

- `Core`
- `monthpos`
- `event`

的分阶段拟合，并统一使用 `Huber + weighted ridge + IRLS` 求解器。

这种做法更强调：

- 鲁棒性
- 组件层级解释
- 数值稳定

而不是完全追求与某个成熟预测库一致的训练形式。

4. **目标不同**

`Prophet` 的目标偏向“预测未来值”。

当前方案 `T1` 的目标偏向：

- 构建可解释基线
- 计算当前偏离
- 发现点异常与持续漂移
- 触发正式重建

所以，当前方案与 `Prophet` 的关系更适合表述为：

> 在 `T1` 的主干结构上，局部借鉴了 `Prophet` 一类加性分解模型的思想，但目标函数、训练方式、漂移处理和系统边界已经明显不同。

### 4.3 当前方案在 `T2 / T3` 上与 `Prophet` 的关系

这里差异就非常大了。

#### `T2`：比例 / 率类

当前方案的 `T2` 不是在原始比例空间直接做简单时序拟合，而是显式处理：

- 分子 / 分母输入
- 分母支撑度
- 平滑比例
- `logit` 空间基线
- 过度离散修正
- 漂移证据累积

`Prophet` 并没有这套比例专属机制。

如果强行用 `Prophet` 建 `error_rate` 之类比例特征，至少会缺少：

- 分母信息的显式使用
- 小分母下不确定性控制
- 比例型异常更自然的方差处理

#### `T3`：分布漂移类

当前方案的 `T3` 处理的是：

- group 分布
- 支持空间
- 固定历史头部集合
- 摘要特征提取
- 模式融合

例如：

- `entropy_shannon`
- `top1_share`
- `out_of_support_share`
- `stable_headK_mix_drift`

这些不是 `Prophet` 的输入对象，也不是 `Prophet` 的建模边界。

`Prophet` 最多只能拿来拟合某个已经被压缩好的单值摘要量，但无法替代：

- `SupportExplicit_T3`
- `StableHeadSet_T3`
- `EvalBasis_T3`
- `support_escape / head_concentration / stable_head_mix_shift`

这一整套 `T3` 机制。

## 5. 技术成熟度与领先性

### 5.1 成熟度

从成熟度看，`Prophet` 明显更强。

它具备：

- 公开论文
- 官方文档
- 开源实现
- 长期使用案例
- 现成 API

而当前方案目前仍是设计规格，虽然结构已经比较完整，但还没有：

- 同等级别的开源实现成熟度
- 大规模回放验证结果
- 性能压测结论
- 线上稳定性证据

因此，如果评价维度是“今天能不能直接落地并稳定使用”，`Prophet` 显然更成熟。

### 5.2 领先性

这里需要拆开看。

如果讨论的是“单序列可解释预测模型”：

- `Prophet` 历史影响力很大
- 但今天更适合被看作成熟基线模型，而不是通用时序预测领域的绝对前沿

如果讨论的是“网络流量异常检测系统设计”：

- 当前方案在系统层面的方向更领先
- 领先点不在于某个单模型公式更前沿
- 而在于它把在线评分、漂移处理、影子基线、正式重建、比例特征、关系分布特征统一到了一个框架里

所以可以这样理解：

- `Prophet`：在“成熟单模型”层面领先
- 当前方案：在“面向流量异常检测的统一系统设计”层面更贴近需求

## 6. 适用范围对比

### 6.1 `Prophet` 更适合的场景

`Prophet` 更适合以下问题：

- 单业务指标预测
- 需要非常强的趋势 / 周期解释
- 时序条数不多
- 离线重拟合可以接受
- 重点是预测和趋势分析，不是高吞吐异常检测

例如：

- DAU / PV / UV 预测
- 销售额预测
- 平台总流量预测
- 单条 KPI 的可解释基线

### 6.2 当前方案更适合的场景

当前方案更适合：

- 海量 `(key, feature)` 序列
- 分钟级在线评分
- 网络流量场景
- 异常检测而不是纯预测
- 需要统一覆盖单值、比例、关系分布

例如：

- 成功率 / 失败率异常
- RTT / 时延类异常
- `serverip:port -> client_group` 分布漂移
- 某服务稳定头部客户端结构变化

## 7. 性能与资源消耗对比

### 7.1 `Prophet` 的性能特征

`Prophet` 本质上是批量拟合模型。

它的问题不在于单条序列一定很慢，而在于：

1. 每条序列都需要单独建模。
2. 新数据到来后，通常仍需重新拟合或做近似 warm start。
3. 如果做交叉验证，成本会进一步放大。

因此：

- 小规模、少量序列时，`Prophet` 完全可用。
- 一旦进入“每分钟海量序列”的系统，成本会非常快地线性放大。

### 7.2 当前方案的性能目标

当前方案从一开始就把性能当作约束写进设计：

- `T1 / T2` 热路径目标是 `O(1)`
- `T3` 摘要提取目标是 `O(nnz)`
- 漂移后先用 `shadow baseline` 托底，再走异步正式重建

这意味着它采用的是典型的“热路径轻、慢路径重”的资源分层思路。

对网络流量系统而言，这比“所有事情都靠重拟合模型解决”更自然。

### 7.3 资源消耗上的本质差异

可以把两者理解成两种完全不同的资源模型：

`Prophet`：

- 模型本身更成熟
- 但偏离线
- 多序列场景资源消耗近似随序列数线性增长

当前方案：

- 在线状态尽量保持 `O(1)`
- 正式训练集中在慢路径
- `shadow baseline` 只保留很小的桥接状态

不过必须强调：

当前方案在资源消耗上的优势，目前是“设计优势”，还不是“实测结论”。在没有实现与压测前，不能正式宣称其性能一定优于 `Prophet` 的工程实现。

## 8. 在网络流量场景下的适配性

### 8.1 `Prophet` 能做什么

在网络流量场景里，`Prophet` 可以做的主要是：

- 某些总量型 `T1` 指标的基线预测
- 某些单值指标的可解释周期建模

例如：

- `bytes_total`
- `conn_count_total`
- 某个服务整体 RTT 中位数

### 8.2 `Prophet` 做不到什么

它很难直接处理：

- 比例型特征的分母支撑度
- 分母很小时的异常强度修正
- 关系分布支持空间
- 稳定头部对象的结构变化
- 在线漂移证据累积
- 影子基线桥接
- 正式重建切换验证

这些恰恰是流量分析系统里最关键的部分。

### 8.3 对当前方案的意义

因此，对我们当前方案而言：

- `Prophet` 不能作为整体替代方案
- 但它可以作为 `T1` 层某些思想的参考基线

更准确地说：

> `Prophet` 对当前方案的价值主要在 `T1` 主干建模思想，而不在 `T2 / T3`，更不在整体系统框架。

## 9. 选型建议

### 9.1 可以借鉴 `Prophet` 的地方

可以借鉴的主要是方法层，而不是实现层：

- 加性分解思想
- 趋势 / 周期 / 事件分层
- 强解释性模型组织方式
- 业务上容易理解的建模语言

### 9.2 不建议直接照搬的地方

不建议直接照搬的有：

- `changepoint` 作为主模型常驻结构
- 以重拟合作为主要更新方式
- 把所有问题都压成单值时序
- 忽略比例分母信息
- 忽略关系分布支持空间

### 9.3 最终建议

最终建议如下：

1. `T1` 可继续把 `Prophet` 视为重要参考对象，但不应把当前方案表述成“Prophet 变体”。
2. `T2 / T3` 不应尝试向 `Prophet` 靠拢，因为问题类型已经不同。
3. 若未来要做实现对照实验，可以把 `Prophet` 作为 `T1` 的离线对照基线，而不是统一框架候选。

## 10. 结论

一句话总结：

- `Prophet` 是成熟、稳健、可解释的单序列预测 / 基线工具。
- 当前方案是面向网络流量异常检测的统一在线基线框架。

前者强在成熟度与现成能力，后者强在场景适配与系统完整性。

因此，两者的关系不是“二选一替代”，而是：

> `Prophet` 可作为 `T1` 局部方法参考，但不足以覆盖当前方案要解决的整体问题。
